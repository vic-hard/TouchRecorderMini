# TouchRecorder-mini

Сквозной пайплайн сбора данных касаний: **Custom View → MotionEvent (включая historical samples) → JSON в `Download/` → Python-валидатор**.

Приложение: один экран, вся площадь — наследник `View` с переопределённым `onTouchEvent`. Внешних зависимостей нет: сбор, сериализация и экспорт сделаны на framework API (`MotionEvent`, `android.util.JsonWriter`, `MediaStore`).

---

## Сборка

Требуется JDK 17+ и Android SDK (`compileSdk` 36.1). Путь к SDK — в `local.properties`.

```bash
# отладочная сборка
./gradlew :app:assembleDebug
# APK: app/build/outputs/apk/debug/app-debug.apk

# сборка для установки на устройство заказчика
./gradlew :app:assembleRelease
# APK: app/build/outputs/apk/release/app-release.apk
```

`release` подписан отладочным ключом — чтобы APK ставился на устройство заказчика без отдельного keystore, который для микротеста избыточен.

`minSdk = 29`: экспорт идёт в общую папку `Download/` через MediaStore, поэтому не нужны ни `WRITE_EXTERNAL_STORAGE`, ни runtime-разрешения. Приложение вообще не запрашивает ни одного permission.

## Как пользоваться

1. Запустить приложение — сессия начинается сразу, `session_id` генерируется при старте Activity.
2. Делать жесты по холсту. В левом верхнем углу в реальном времени: `события: N / исторических сэмплов: M`. Рисуется след последнего жеста (в том числе по историческим точкам).
3. **Экспорт** — сохраняет сессию в `Download/touch_session_<дата>_<время>_<id>.json`, показывает toast с именем файла и сводкой.
4. **Поделиться** — становится активной после экспорта, отправляет сохранённый файл стандартным chooser'ом.

Перезапуск приложения начинает новую сессию с обнулёнными счётчиками.

## Запуск валидатора

Только стандартная библиотека Python 3 (`json`, `sys`, `statistics`), без pip-зависимостей:

```bash
python validate.py session.json
```

Код выхода: `0` — проверки пройдены, `1` — есть ошибки валидации.

Что проверяется:

1. Файл — валидный JSON, присутствуют все обязательные поля (структура сессии, метаданные устройства, поля каждого события и каждого исторического сэмпла) и их типы.
2. `event_time_ms` неубывающе внутри каждого жеста.
3. Таймстемпы в `history` неубывающие и не больше `event_time_ms` родительского события.
4. Статистика в stdout: число жестов, событий, исторических сэмплов; доля `move` с непустым `history`; длительность каждого жеста.
5. Предупреждения (не влияют на код выхода): если `pressure`, `size` или `touch_major` константны по всей сессии.

## Структура кода

| Файл | Роль |
| :--- | :--- |
| `recorder/TouchRecorder.kt` | **Ядро.** Публичный API: `start()`, `feed(MotionEvent)`, `stats()`, `export()`, `stop()`. Про Activity, View и разметку не знает ничего. |
| `recorder/Models.kt` | `TouchEventRecord`, `HistorySample`, `Gesture`, `SessionMeta` — immutable-объекты, безопасные для передачи между потоками. |
| `recorder/SessionJsonWriter.kt` | Потоковая сериализация в JSON. |
| `recorder/DownloadsExporter.kt` | Запись в `Download/` через MediaStore, возврат `content://` Uri. |
| `ui/TouchCanvasView.kt` | Наследник `View`: отдаёт `MotionEvent` в рекордер и рисует след. |
| `MainActivity.kt` | Связывание UI с рекордером: счётчики, кнопки, экспорт в фоне. |
| `validate.py` | Валидатор сессии. |
| `reference_session.json` | Эталонная сессия, записанная на устройстве исполнителя (см. последний раздел). |

Граница «библиотека / UI» проходит по пакету `recorder`: чтобы вынести его в отдельный модуль, достаточно перенести пакет — из UI он не использует ничего.

### Потоковая модель

```
UI-поток                      worker-поток              поток экспорта
────────                      ────────────              ──────────────
onTouchEvent
  копирование полей
  MotionEvent + history
  queue.put(record) ─────────► take()
  счётчики (AtomicLong)         append() в список
                                жестов
                             ◄── SnapshotRequest ─────── export()
                                копия жестов ──────────► JsonWriter → MediaStore
```

UI-поток делает ровно две вещи: снимает значения с `MotionEvent` (это обязано происходить синхронно, см. ниже) и кладёт готовую запись в `LinkedBlockingQueue`. Сериализация и запись файла не выполняются на UI-потоке никогда.

Накопленный список жестов трогает только worker. Экспорт не читает его напрямую, а посылает в очередь `SnapshotRequest`; worker сам делает копию и отдаёт её через `ArrayBlockingQueue`. Так список остаётся однопоточным, публикация копии даёт корректную видимость памяти без синхронизации, а сбор событий не блокируется на время сериализации.

## Что было сложным и какие баги поймали

**Граница потоков и время жизни `MotionEvent`.** Первое, обо что легко разбиться в такой задаче, — желание отдать сам `MotionEvent` в фоновый поток и разобрать его там, чтобы «не грузить UI». Так делать нельзя: система переиспользует объекты событий, и после возврата из `onTouchEvent` содержимое уже не ваше — в лучшем случае получите данные следующего касания, в худшем — мусор, который никак не отличить от валидных данных. Поэтому в `feed()` на UI-потоке выполняется полное копирование, включая цикл по историческим сэмплам, и только потом immutable-запись уходит в очередь. Отсюда же решение считать экранные счётчики на UI-потоке в момент постановки в очередь, а не в worker'е: счётчики нужны заказчику для визуальной проверки, и они не должны отставать от пальца, если worker чем-то занят.

**Работа с индексами указателей и историей.** Второй неочевидный момент — API исторических сэмплов несимметричен: координаты берутся с индексом указателя (`getHistoricalX(pointerIndex, pos)`), а вот `getHistoricalEventTime(pos)` — без него, потому что время относится ко всему пакету событий, а не к отдельному пальцу. Перепутать легко, компилятор не поможет. Связанная ловушка — индекс указателя не равен его id и меняется, когда пальцы поднимаются: если писать `getX(0)`, то после касания вторым пальцем данные незаметно начнут приходить от чужого пальца. Поэтому на `ACTION_DOWN` запоминается `pointerId` и дальше индекс каждый раз ищется через `findPointerIndex`, а `ACTION_POINTER_DOWN/UP` игнорируются целиком — по ТЗ пишем только основной указатель. Ещё одно осознанное решение: `historySize` читается для событий любого типа, а не только для `move` — наличие истории определяется тем, как система склеила пакет, а не типом события.

**Сериализация и экспорт.** Здесь поймали три конкретных бага. Первый: `JsonWriter.value(float.toDouble())` печатает `0.42f` как `0.41999998688697815` — расширение float до double тащит за собой мусор точности; лечится записью через `BigDecimal(v.toString())`, тогда в файле остаётся `0.42`. Второй: `pressure`/`size` у некоторых драйверов приходят как `NaN`, а `NaN` — невалидный JSON, и валидатор падал бы на разборе; такие значения пишем как `null`, а валидатор их допускает и просто исключает из проверки на константность. Третий, уже в MediaStore: без флага `IS_PENDING` файл виден другим приложениям ещё во время записи, и «Поделиться» может утащить обрезанный JSON — поэтому запись идёт под `IS_PENDING=1` со сбросом в 0 после закрытия потока, а при ошибке записи запись в MediaStore удаляется, чтобы в `Download/` не оставался нулевой файл. Отдельно по сборке: шаблон Android Studio тянул `androidx.core:core-ktx:1.19.0`, который требует `compileSdk 37` и валил сборку; так как из него в проекте ничего не использовалось, зависимость просто убрана — теперь у приложения нет внешних зависимостей вообще.

## Эталонная сессия и особенности устройства

`reference_session.json` — сессия по сценарию приёмки (одиночный тап, медленный свайп, быстрый свайп), записанная пальцем на **Samsung Galaxy A52 (SM-A525F), Android 14 (SDK 34), 1080×2400**. Валидатор на ней возвращает 0:

```
жестов: 3, событий: 146, исторических сэмплов: 271
move с непустым history: 137 из 140 (97.9%), в среднем 1.98 сэмпла на событие
жест 1 (тап):            79 мс,   6 событий,   7 сэмплов
жест 2 (медленный свайп): 1455 мс, 129 событий, 247 сэмплов
жест 3 (быстрый свайп):   111 мс,  11 событий,  17 сэмплов
```

**Historical samples устройство предоставляет.** Почти все `move` приходят с непустой историей; три события без неё — нормальный случай, когда система доставила пакет из одного сэмпла. Хорошо видно и зачем история вообще нужна: на медленном свайпе медианный интервал между доставленными событиями — 11 мс при максимуме 51 мс, и без исторических точек в этих провалах терялась бы часть траектории.

**Ограничение устройства: `pressure` константно и равно 1.0.** Тачскрин A52 не отдаёт градации давления — вместо этого приходит бинарное «касание есть». Валидатор на эталонной сессии печатает по этому поводу `WARNING`, это ожидаемое поведение, а не ошибка данных. Остальные поля живые: `size` меняется в диапазоне 0.0039…0.051, `touch_major`/`touch_minor` — 0.42…5.52. На устройстве заказчика (Samsung, Android 13+) поведение `pressure` может отличаться — предупреждение валидатора в любом случае не влияет на код выхода.
